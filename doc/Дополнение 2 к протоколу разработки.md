## 29. Что изменилось относительно v2

**Три ключевых сдвига:**

1. **`team.json` v4.** У агентов больше нет `port` и `pid`. Порты назначаются **автоматически** из `port_range` проекта при старте (`_allocate_port`). `team.json` хранит только `id`, `name`, `script`, `autostart`, `orchestrator_template`, `source*`, `env`. Миграция v3 → v4 автоматическая при `Project.open`.
2. **Модель «процессы переживают дашборд».** `atexit` / `_cleanup_children` **убраны** из `launch`. Ctrl+C **не убивает** детей. Они продолжают работать. При следующем `Project.open` дашборд **усыновляет** живых агентов (`_scan_and_adopt`), а не перезапускает.
3. **Идентичность агента через env.** `FONA_AGENT_NAME` и `FONA_TEAM_NAME` передаются ребёнку через `_child_env`. `/api/v1/model` отдаёт их как `agent_name` и `team_name`. Это единственный способ отличить «наш» процесс от «чужого» на порту.

**Побочные следствия:**

- **`poll` — наблюдатель.** Не убивает, не перезапускает. При `pid mismatch` ставит `error: stale killed, press Start`. Это **ломает** бесконечный цикл `kill → start → kill`, который был в v2.
- **Вкладка `Adopted` в UI.** Показывает **все** живые агенты в `port_range`, включая ручные запуски, чужие команды и осиротевшие процессы. Колонки: Team / Name / Port / PID / Status / Actions (Open UI, Kill).
- **`Stop` для adopted = «отпустить».** Не убивает процесс. Для явного убийства — кнопка `Kill` во вкладке `Adopted` или `taskkill` вручную.
- **`live_scan.py` — новый модуль.** Один `netstat`/`lsof` на диапазон + параллельные HTTP-запросы. Используется в `_refresh`, `_do_load`, `_on_project_open`, `_scan_and_adopt`.

**Файлы, затронутые в v3:**

| Файл | Статус |
|---|---|
| `fona/dashboard.py` | **переписан** (v4) |
| `fona/server.py` | изменён `/api/v1/model` (добавлены `agent_name`, `team_name`) |
| `fona/live_scan.py` | **новый** |
| `fona/team.py` | без изменений (v4 совместим: `port` отсутствует → `team_resolver` вернёт `None`) |
| `fona/__init__.py`, `fona/agent.py`, `fona/config.py`, `fona/peers.py`, `fona/protocol.py`, `fona/ui.py`, `fona/orchestrator_app.py`, `fona/orchestrator_ui.py` | без изменений |

## 30. `team.json` v4 — формат и миграция

**Формат v4:**

```json
{
  "version": 4,
  "name": "warehouse_team",
  "port_range": [8020, 8099],
  "saved_at": "2026-11-09T12:00:00",
  "agents": [
    {
      "id": "60a827fb",
      "name": "WH",
      "script": "scripts/warehouse_agent.py",
      "autostart": true,
      "source": "...",
      "source_sha256": "...",
      "source_mtime": 1794070972.93,
      "orchestrator_template": null,
      "env": {}
    }
  ]
}
```

**Правила:**

- `port` **не хранится**. Порт назначается при `start` из `port_range` через `_allocate_port`. Если пользователь хочет «прибить» агента к конкретному порту — он этого сделать не может; это **осознанно** (см. §32).
- `orchestrator_gradio_port` **не хранится**. Тоже назначается из `port_range`.
- `pid` **не хранится**. PID нестабилен, при перезапуске другой.
- `env` — per-agent env. Пользователь задаёт через `team.json` вручную (UI для env убран — §4.6).
- `name` — **уникальное** в рамках `team.json`. `_scan_and_adopt` использует его как ключ.

**Миграция v3 → v4** (при `Project.open`):

1. Прочитать `team.json`.
2. Если `version == 3`:
   - Удалить из каждого агента `port` и `orchestrator_gradio_port`.
   - Удалить `port_range` из агентов (если был).
   - Добавить `port_range` в корень: `[min(old_ports), max(old_ports) + 10]` (или `[8020, 8099]`, если старых портов не было).
   - Сохранить как v4.
3. Если `version ∈ {1, 2}` — аналогично, но с дефолтным `port_range`.
4. Если `version == 4` — без изменений.

**Файл `children.json` упразднён.** Runtime-состояние (какие процессы живы) — это то, что сканируется через `live_scan.scan_range` при `Project.open`, а не файл. Если нужен «журнал запусков» для отладки — писать в `<project>/logs/runtime.log` (текстовый), но не парсить его для логики.

## 31. Модель «процессы переживают дашборд»

**Что это значит:**

- При `Ctrl+C` дашборда дети **не убиваются**. `atexit` и `_cleanup_children` убраны из `launch`.
- При следующем `Project.open` дашборд **сканирует** `port_range` и **усыновляет** живых агентов (`_scan_and_adopt`).
- «Усыновление» = `AgentEntry` с `adopted=True`, `process=None`, `port=<найденный>`. Дашборд знает о процессе, но **не владеет** им.

**Что это даёт:**

- Агент продолжает работать, пока пользователь не нажмёт `Stop` / `Kill` / не убьёт вручную.
- Перезапуск дашборда **не** рвёт работу команды.
- Ручной запуск агента (`python warehouse_agent.py`) **виден** в дашборде (если `team_name` + `agent_name` выставлены — §33).

**Что это ломает:**

- **`Stop` для adopted ≠ `Stop` для своего.** Своего `Stop` убивает (`_stop_process`), adopted — «отпускает» (`_do_not_adopt.add`, `adopted=False`, процесс жив). Для явного убийства — `Kill` во вкладке `Adopted`.
- **`Load and start` не перезапускает усыновлённых.** `load_team` сначала усыновляет, потом для не-усыновлённых делает `start`.
- **`Remove` adopted — «отпустить без записи»**, не убить.

**Что нельзя делать в этой модели:**

- **Не убивать детей при выходе.** Это нарушит контракт.
- **Не убивать adopted через `Stop`.** Это убьёт ручной процесс, который пользователь не планировал останавливать.
- **Не перезапускать из `poll`.** Это ломает бесконечный цикл `kill → start → kill` (§35).

## 32. Авто-назначение портов

**Алгоритм `_allocate_port`:**

```python
def _allocate_port(used: set, range_start: int, range_end: int) -> int:
    for port in range(range_start, range_end + 1):
        if port in used:
            continue
        if _is_port_free(port):
            return port
    raise RuntimeError(f"no free port in range {range_start}..{range_end}")
```

**Где вызывается:**

- `AgentManager.start` — перед `Popen`. `used` — порты всех агентов в `_manager` (`a.port`).
- `orchestrator_app` — по тому же принципу (если оркестратор запускается как отдельный процесс).

**Почему не назначается вручную:**

- Пользователь не должен думать о портах. Диапазон — свойство **проекта**, а не агента.
- Порт — **эфемерный** идентификатор: после `Stop`/`Start` агент может получить другой порт (если старый занят).
- `team.json` не хранит порт → нет рассинхронизации между `team.json` и реальным портом.
- `Open UI` в карточке всегда работает: `a.port` — актуальный.

**Что это ломает:**

- `team_resolver` из `fona/team.py` **не может** вернуть URL пира: в `team.json` нет `port`. `call_peer` идёт через `FONA_PEERS` (или `resolver=team_resolver`, который вернёт `None`).
- Для **меж-агентного взаимодействия** нужно либо:
  - задать `FONA_PEERS` вручную в `team.json` (`env: {"FONA_PEERS": "worker=http://127.0.0.1:8020"}`), либо
  - обновить `team_resolver`, чтобы он **сканировал** `port_range` и сопоставлял `agent_name` → `port` (это **RFC** на `fona/team.py` — §36).

**Текущее состояние `team_resolver`:** для v4 возвращает `None` (в `team.json` нет `port`). `call_peer` идёт в `cfg.peers`. Если `cfg.peers` пуст — `"err:unknown peer <name>"`. Это **известное ограничение** (§36).

## 33. Идентичность агента: `FONA_AGENT_NAME` и `FONA_TEAM_NAME`

**Env-переменные:**

| Переменная | Что значит | Кто ставит |
|---|---|---|
| `FONA_AGENT_NAME` | имя агента в `team.json` | `_child_env` в `dashboard.py` |
| `FONA_TEAM_NAME` | имя проекта (= `Project.name`) | `_child_env` в `dashboard.py` |
| `FONA_PORT` | фактический порт | `_child_env` в `dashboard.py` |
| `FONA_TEAM_FILE` | путь к `team.json` | `_child_env` в `dashboard.py` |
| `FONA_CHILD` | `"1"` для детей | `_child_env` в `dashboard.py` |

**`/api/v1/model` (в `fona/server.py`):**

```python
return {
    ...
    'agent_name': os.getenv('FONA_AGENT_NAME') or None,
    'team_name': os.getenv('FONA_TEAM_NAME') or None,
}
```

**Использование:**

- **`_scan_and_adopt`** усыновляет только если `team_name == project.name` **и** `agent_name` есть в `team.json`.
- **Вкладка `Adopted`** показывает `team_name` из ответа. Если `team_name == current_team` — подсвечивает `team-ours`.
- **Ручной запуск с env** эквивалентен запуску через дашборд с точки зрения усыновления:

  ```bash
  FONA_AGENT_NAME=WH FONA_TEAM_NAME=warehouse_team \
      python examples/warehouse_team/warehouse_agent.py
  ```

**Ручной запуск без env:**

- `agent_name=None`, `team_name=None` → **не** усыновляется.
- Вкладка `Adopted`: `Team=—`, `Name=?`, `Port=8020`, `Status=online`.
- Пользователь может `Open UI` / `Kill`, но не «управлять» как агентом команды.

**Это правильно:** дашборд не присваивает процессы, которые пользователь явно не пометил как свои.

@app.post("/dashboard/kill_live")
async def dash_kill_live(request: Request):
    port = int(request.query_params.get("port"))
    pid = _find_pid_by_port(port)
    if not pid:
        return {"status": "error", "error": "no listener"}
    image = _get_process_image(pid)
    if image and not image.lower().startswith("python"):

## 35. `poll` — наблюдатель, не менеджер

**Что `poll` делает:**

- Читает `/api/v1/health`, `/api/v1/model`.
- Обновляет `status`, `rules`, `actions`, `latency_ms`, `history`.
- При `pid mismatch` (на порту отвечает **не** наш `a.process.pid`):
  - Убивает **старый** (`_kill_python_on_port`).
  - Убивает **свой** мёртвый (`if _is_pid_alive(a.process.pid)`).
  - Ставит `status="error"`, `error="port N serves pid=X, expected Y; stale killed, press Start"`.
  - **Не** перезапускает.

**Что `poll` НЕ делает:**

- Не вызывает `start`.
- Не убивает adopted (`a.adopted=True`).
- Не меняет `a.port` (кроме `auto-corrected` из логов).

**Почему:**

- **Бесконечный цикл.** В v2 `poll` при `pid mismatch` вызывал `self.start`, что создавало новый процесс, который не мог занять порт (старый жив), `poll` видел stale → `pid mismatch` → `start` → ... Цикл. Теперь `poll` только сигналит.
- **Наблюдатель.** `poll` — это «что вижу, то и говорю». Менеджмент — только явные действия пользователя (`Start`/`Stop`/`Restart`/`Kill`).

**Единственное исключение:** `port auto-corrected` из логов (`_detect_uvicorn_port_from_logs`). Это не «перезапуск», а «у агента порт в `PROGRAM` не совпал с `FONA_PORT`, поэтому `a.port` подправляется, чтобы `Open UI` работал».

## 36. Известные ограничения и TBD

### 36.1. `team_resolver` для v4 возвращает `None`

**Симптом:** `call_peer("warehouse", ...)` → `"err:unknown peer warehouse"`, если `FONA_PEERS` не задан.

**Причина:** `team.py` ищет `port` в `team.json`, а в v4 его нет.

**Варианты решения:**

- **A.** В `team.json` в `env` каждого агента явно прописать `FONA_PEERS` с URL других агентов. Минус: URL содержат порты, которые назначаются при старте → нельзя задать заранее.
- **B.** Обновить `team_resolver`, чтобы он **сканировал** `port_range` (через `live_scan.scan_range`) и сопоставлял `agent_name` → `port`. Это **RFC** на `fona/team.py`: `team_resolver` становится «живым» — кеширует результат на N секунд, инвалидирует по таймауту. Минус: `team_resolver` теперь зависит от `live_scan`; это добавляет `httpx` в `team.py`.
- **C.** Передавать `FONA_PEERS` в `env` ребёнка из `_child_env` **после** того, как все агенты назначили порты. Но `start` вызывается **по одному** (`load_team` → `for aid: start`), и на момент старта первого агента порты остальных ещё неизвестны. **Не работает** для первого агента.
- **D.** Добавить в `_child_env` lazy-resolver: агент **не** получает `FONA_PEERS` статически, а при `call_peer` идёт в `FONA_TEAM_FILE` + `FONA_AGENT_NAME`, читает `team.json`, делает `scan_range` **в момент вызова**. Это по сути **B**, но в `fona/peers.py`.

**Рекомендация:** **B** (обновить `team_resolver`) или **D** (обновить `peers.py`). B чище: `team_resolver` — это как раз «где живёт агент с таким именем», и в v4 «где живёт» = «на каком порту сканер его найдёт». Требует RFC.

### 36.2. `_scan_and_adopt` и `scan_range` дублируют логику

**Симптом:** `_scan_and_adopt` делает `_is_port_open` + `httpx.get("/api/v1/model")` вручную; `live_scan.scan_range` делает то же самое.

**Решение:** переписать `_scan_and_adopt` через `scan_range` (см. §38.3). Сократит `dashboard.py` на ~40 строк и гарантирует единый источник правды для «что на порту».

### 36.3. Orphan-cleanup не реализован

**Симптом:** если дашборд убит через `taskkill /F`, его дети остаются живы. При следующем `Project.open` они **усыновляются** (правильно), но `children.json` больше нет — если пользователь хочет «убить всех сирот», нужна отдельная кнопка `Stop all` (её нет в UI, только в `_do_load` нет).

**Решение:** добавить кнопку `Stop all` в UI (`AgentManager.stop_all()` уже есть). Или `/dashboard/stop_all` endpoint.

### 36.4. `Stop` для adopted — сюрприз

**Симптом:** пользователь нажимает `Stop` на adopted → процесс **жив**, статус `stopped`. Пользователь ожидает «убить».

**Решение:** две кнопки в карточке для adopted: `Release` (отпустить) и `Kill` (убить). Сейчас `Stop` = `Release`, `Kill` только во вкладке `Adopted`. Можно добавить `Kill` в карточку для adopted.

### 36.5. Auto-restart при `pid mismatch` не реализован

**Симптом:** `poll` ставит `error: stale killed, press Start`. Пользователь нажимает `Start`. Если stale **не убит** (`taskkill` требует прав администратора), `start` упадёт на `_is_port_free` → `error: port in use`. Пользователь меняет порт через ⚙ (кнопки нет) или `Kill` во вкладке `Adopted`.

**Решение:** добавить кнопку `Restart` в карточку для adopted. Или `Kill` в карточку для adopted.

### 36.6. `env` в UI убран

**Симптом:** пользователь не может задать `env` для агента из UI. Только через `team.json` вручную.

**Решение:** либо оставить как есть (env — для продвинутых), либо вернуть поле в UI с форматом `KEY=VALUE` (по строке).

### 36.7. `orchestrator_gradio_port` не назначается

**Симптом:** `orchestrator_gradio_port` в `AgentEntry` есть, но `_allocate_for` возвращает `0` (`agent_port, 0`). Если пользователь хочет оркестратор — нужно задать `orchestrator_gradio_port` вручную, а в v4 его нет.

**Решение:** либо вернуть `orchestrator_gradio_port` в `team.json` (как отдельное поле, назначаемое вручную), либо `_allocate_for` выделяет **два** порта из диапазона.

### 36.8. `team.json` v3 миграция не реализована

**Симптом:** `load_team` читает `version` и принимает `1, 2, 3, 4`, но **не** мигрирует. Если `team.json` v3 (с `port`), `_dict_to_agent` **игнорирует** `port` (в v4 нет поля). Миграция не нужна для работы, но `Save` перезапишет v3 в v4 (без `port`). Это работает, но **не** переносит `port_range` из v3 (его нет). Дефолт `[8020, 8099]` при `Project.open`, если `port_range` нет.

**Решение:** добавить `_migrate_v3_to_v4` в `Project.open`. См. §30.

## 37. Что следующему чату нельзя менять без RFC

- **Семантические контракты §6** (v1): `@agent.program` prepend, `action` при `None`/исключении → fail, `effect` → успех, `generate` при пустом → fail, `context` передаётся, `query_one` в HITL — первое решение, `generate` в REST — все решения, `from_hub` с `revision` фиксирует коммит.
- **Prepend-семантика `@agent.program`** для HF (§2 P2 v1).
- **`Database` под `api_lock`** (§2 P6 v1).
- **Публичный API** (`Agent`, `agent`, декораторы) — только через §12 (deprecation cycle).
- **Формат `team.json`** — обратная совместимость. v4 читает v1–v3.
- **Модель «процессы переживают дашборд»** (§31). Не убивать детей при выходе.
- **`poll` — наблюдатель** (§35). Не перезапускать из `poll`.

## 40. Резюме в одном абзаце

**Fona v3 перешла на модель «процесс = источник правды, а не JSON».** `team.json` v4 больше не хранит `port` и `pid`; порты назначаются из `port_range` при старте; процессы переживают дашборд; при следующем открытии проекта дашборд **усыновляет** живых по `FONA_TEAM_NAME` + `FONA_AGENT_NAME`; `poll` — наблюдатель, не менеджер; `Stop` для adopted = «отпустить», `Kill` во вкладке `Adopted` = убить. Вкладка `Adopted` показывает **все** live-агенты в `port_range`, включая ручные запуски и чужие процессы. Это устраняет корень всех проблем v2 (`stale process on port`, `pid mismatch`, `kill → start → kill`) — но оставляет один открытый вопрос: **как агенты находят друг друга без статического `port` в `team.json`** (§36.1). Решение — RFC на `team_resolver`, который сканирует `port_range` в момент вызова, либо на `peers.py` с lazy-резолвером. До этого меж-агентное взаимодействие работает только через явный `FONA_PEERS` в `env`.
